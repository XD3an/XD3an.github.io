Python 一篇封神：從基本語法、常用套件到 CPython 底層技術

語法、套件、實務寫法，再一路拆到 bytecode、PyObject、GC 與 GIL，搞懂每一行 Python 背後發生了什麼事

By XD3an

TL;DR

一篇把 Python 從「會寫」帶到「知道它在幹嘛」的完整筆記，分四段：

  • 基本語法：名稱綁定、容器、函式、推導式、類別、例外，每個都順便講它背後的規則。
  • 常用套件：標準函式庫裡該熟的那幾個，加上資料、Web、工具鏈、資安各領域的主流選擇。
  • 實務常用方法：虛擬環境、型別提示、dataclass、pathlib、logging、併發怎麼選、效能怎麼量。
  • 底層技術：CPython 怎麼把 .py 變成 bytecode、直譯器迴圈怎麼跑、物件在記憶體長什麼樣、GC 與 GIL 在做什麼。

前言：Python 沒有你以為的那麼「直譯」

很多人學 Python 的第一堂課就聽過一句話：「Python 是直譯式語言。」這句話不算錯，但會讓人誤會很久。

你按下 python app.py 的那一刻，CPython 做的第一件事其實是編譯：把原始碼切成 token、解析成抽象語法樹（AST），再編譯成 bytecode，最後才交給一個用 C 寫的迴圈一條一條執行。__pycache__ 資料夾裡那些 .pyc，就是編譯完存下來的成品。

所以 Python 不是「不編譯」，是「編譯成虛擬機指令再直譯」。這個差別看起來很學術，但它會解釋很多實務上的現象：為什麼 local 變數比 global 快、為什麼 3.11 之後突然變快、為什麼多執行緒跑 CPU 密集工作沒有變快。

一行 Python 程式碼從原始碼到被執行的路徑，以及執行時一路陪著跑的四個機制。

這篇文章前三段是使用者視角（怎麼寫、用什麼、實務怎麼做），最後一段換到 CPython 的視角，把前面那些「規則」背後的原因補上。版本以 CPython 3.12–3.14 為主，有版本差異的地方會標出來。

Part 1：基本語法

變數不是盒子，是名牌

先破除一個最常見的迷思：Python 的變數不是裝值的盒子，而是貼在物件上的名牌（name binding）。a = [1, 2] 的意思是「建立一個 list 物件，然後把名稱 a 綁到它身上」。

a = [1, 2]
b = a          # 不是複製，是再貼一張名牌到同一個物件
b.append(3)
print(a)       # [1, 2, 3]
print(a is b)  # True：同一個物件

c = a.copy()   # 淺複製（shallow copy）才是新物件
print(a == c, a is c)  # True False

這裡順便分清楚兩個運算子：

  • ==：值相不相等，呼叫的是 __eq__。
  • is：是不是同一個物件，比的是身分（identity），CPython 上就是記憶體位址。只有跟 None 這類單例（singleton）比較時才該用 is。

型別跟著物件走，不跟著名稱走。同一個名稱可以先綁 int 再綁 str，這就是「動態型別」；但 "1" + 1 會直接丟 TypeError，不會偷偷轉型，這是「強型別」。動態跟強型別是兩件事，常被混在一起講。

常用的基本型別：

  • int：任意精度，不會溢位，2 ** 1000 照樣算得出來。
  • float：就是 C 的 double，所以 0.1 + 0.2 != 0.3。要精確小數用 decimal.Decimal，要分數用 fractions.Fraction。
  • str：Unicode 字串，不可變（immutable）。
  • bytes / bytearray：原始位元組。處理檔案、網路封包、二進位格式時用它，跟 str 之間要明確 encode() / decode()。
  • bool：其實是 int 的子類別，True + True == 2。
  • None：唯一的「沒有值」。

內建容器：list、tuple、dict、set

四個容器撐起了九成的 Python 程式。挑哪一個，取決於兩個問題：要不要改、要怎麼找。

  • list：有序、可變。尾端 append/pop 是 O(1)，insert(0, x) 和 x in lst 是 O(n)。
  • tuple：有序、不可變。拿來表示「一筆固定結構的資料」，也能當 dict 的 key。
  • dict：key → value 的雜湊表，查找平均 O(1)。從 3.7 開始，保留插入順序是語言規格，不再只是實作細節。
  • set：不重複元素的集合，x in s 平均 O(1)，交集、聯集、差集一行搞定。
users = {"alice": 30, "bob": 25}
users.get("carol", 0)                  # 找不到給預設值，不丟 KeyError
users.setdefault("carol", 20)

for name, age in users.items():        # 同時拿 key 和 value
    print(f"{name=} {age=}")           # 3.8+ 的 f-string 除錯寫法

seen = set()
ips = ["10.0.0.1", "10.0.0.2", "10.0.0.1"]
unique = [ip for ip in ips if not (ip in seen or seen.add(ip))]  # 保序去重

a, *rest, last = [1, 2, 3, 4, 5]       # 解包（unpacking）
merged = {**users, "dave": 40}         # dict 合併；3.9+ 也可以寫 users | {"dave": 40}

一個實務判斷：如果你在 list 上頻繁做 in 查詢，資料一多就會慢下來。換成 set 或 dict，複雜度從 O(n) 降到 O(1)，這比任何微優化都有感。

流程控制與 match

if / for / while 大家都會，幾個比較少人知道但很好用的點：

  • Truthiness：空容器、0、""、None 都是假。寫 if items: 就好，不用 if len(items) > 0:。
  • for ... else：迴圈沒有被 break 才會進 else，適合「找不到」的情境。
  • 海象運算子 :=（3.8+）：在運算式裡同時賦值。
  • match（3.10+）：結構化模式比對（structural pattern matching），不是 switch，是能拆解資料結構的比對。
while (line := f.readline()):
    handle(line)

def handle_event(event: dict):
    match event:
        case {"type": "login", "user": str(user)}:
            print(f"{user} 登入")
        case {"type": "error", "code": int(code)} if code >= 500:
            print(f"伺服器錯誤 {code}")
        case {"type": t}:
            print(f"未處理的事件 {t}")
        case _:
            print("格式不對")

函式、參數與作用域

Python 的函式是一等公民（first-class object）：可以存進變數、當參數傳、當回傳值。這一點是後面裝飾器、callback、functools 全部的基礎。

參數的五種形態

def f(pos_only, /, normal, *args, kw_only, **kwargs):
    ...

# pos_only：只能用位置傳（3.8+ 的 /）
# normal：位置或關鍵字都行
# *args：多出來的位置參數，收成 tuple
# kw_only：* 之後的只能用關鍵字傳
# **kwargs：多出來的關鍵字參數，收成 dict

經典陷阱：可變的預設值

def add_item(item, bucket=[]):   # 錯：預設值只在 def 執行時建立一次
    bucket.append(item)
    return bucket

add_item(1)  # [1]
add_item(2)  # [1, 2]  ← 共用同一個 list

def add_item(item, bucket=None): # 對：用 None 當哨兵
    if bucket is None:
        bucket = []
    bucket.append(item)
    return bucket

這不是 bug，是規則：def 是一個「執行時才發生」的陳述式，預設值在那一刻被求值、存在函式物件的 __defaults__ 裡。

作用域：LEGB

找名稱的順序是 Local → Enclosing → Global → Builtins。要在內層改外層的變數，得明講：global 改模組層級，nonlocal 改外層函式。

閉包與裝飾器

內層函式記住外層變數，就是閉包（closure）。裝飾器（decorator）只是「接收一個函式、回傳一個新函式」的語法糖：

import functools
import time

def timed(func):
    @functools.wraps(func)          # 保留原函式的名稱與 docstring
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return func(*args, **kwargs)
        finally:
            print(f"{func.__name__} 花了 {time.perf_counter() - start:.3f}s")
    return wrapper

@timed            # 等同於 fetch = timed(fetch)
def fetch(url): ...

推導式、迭代器與生成器

推導式（comprehension）是 Python 最有辨識度的語法：

squares = [x * x for x in range(10) if x % 2 == 0]
index   = {name: i for i, name in enumerate(names)}
exts    = {p.suffix for p in paths}
total   = sum(x * x for x in range(10**7))   # 生成器運算式：不建 list，省記憶體

背後的機制是迭代協定（iterator protocol）：

  • Iterable：有 __iter__，能被 iter() 變出一個 iterator。list、dict、檔案都是。
  • Iterator：有 __next__，每次吐一個值，吐完丟 StopIteration。

for x in obj 其實就是：先 it = iter(obj)，然後不斷 next(it)，直到 StopIteration。

生成器（generator）是寫 iterator 最省力的方式：函式裡有 yield，呼叫它就不會立刻執行，而是回傳一個「暫停中的函式」。

def read_large_log(path):
    with open(path, encoding="utf-8") as f:
        for line in f:
            if "ERROR" in line:
                yield line.rstrip()

for err in read_large_log("app.log"):   # 一次只有一行在記憶體裡
    print(err)

重點不是語法，是惰性求值（lazy evaluation）：資料要用的時候才生出來。處理幾 GB 的 log、串流資料、無限序列時，生成器是記憶體不爆掉的關鍵。標準函式庫的 itertools 就是一整套生成器積木。

類別與資料模型（dunder methods）

Python 的 OOP 核心不是繼承，是資料模型（data model）：你實作特定的雙底線方法（dunder method），你的物件就能跟語言內建的語法互動。

class Vector:
    def __init__(self, x: float, y: float):
        self.x, self.y = x, y

    def __repr__(self):           # print / 除錯時看到的樣子
        return f"Vector({self.x}, {self.y})"

    def __add__(self, other):     # 讓 v1 + v2 能用
        return Vector(self.x + other.x, self.y + other.y)

    def __eq__(self, other):      # 讓 == 能用
        return (self.x, self.y) == (other.x, other.y)

    def __len__(self): ...        # len(v)
    def __iter__(self): ...       # for c in v
    def __getitem__(self, i): ... # v[0]
    def __enter__(self): ...      # with v:
    def __call__(self): ...       # v()

「Pythonic」這個詞講的就是這件事：不是去呼叫 v.getLength()，而是讓 len(v) 自然成立。

幾個常用的類別工具：

  • @property：把方法偽裝成屬性，需要驗證或計算時才用，不要每個欄位都包 getter/setter。
  • @classmethod：拿到的是類別本身，常拿來寫替代建構子，例如 User.from_json(data)。
  • @staticmethod：跟類別放在一起但不需要 self 或 cls 的函式。
  • super()：呼叫 MRO 上的下一個類別，不是「父類別」，多重繼承時差很多（Part 4 會講 MRO）。

例外處理與 with

Python 的文化是 EAFP（Easier to Ask Forgiveness than Permission）：先做，出錯再處理；而不是 LBYL（Look Before You Leap）：先檢查一堆條件再做。

try:
    config = json.loads(path.read_text(encoding="utf-8"))
except FileNotFoundError:
    config = {}
except json.JSONDecodeError as e:
    raise ConfigError(f"{path} 格式錯誤") from e   # 保留原始例外鏈
else:
    validate(config)        # 沒出錯才跑
finally:
    cleanup()               # 一定會跑

兩條實務規則：

  • 不要寫裸的 except:，它連 KeyboardInterrupt 都會吃掉。至少寫 except Exception，最好寫具體的例外。
  • 自訂例外繼承 Exception，用類別階層表達錯誤種類，呼叫端才能精準接。

3.11 加入了 ExceptionGroup 和 except*，用來處理「同時發生好幾個錯誤」的情境（例如 asyncio 的 TaskGroup 裡多個 task 一起失敗）。

with 陳述式則是「資源一定會被釋放」的保證。檔案、鎖、資料庫連線、暫存目錄，全部都該用 with。自己寫 context manager 最快的方式是 contextlib.contextmanager：

from contextlib import contextmanager

@contextmanager
def chdir_temp(path):
    old = os.getcwd()
    os.chdir(path)
    try:
        yield
    finally:
        os.chdir(old)     # 中間出例外也會跑回來

（3.11 之後標準函式庫已經內建 contextlib.chdir，這裡只是示範寫法。）

Part 2：常用套件

Python 的口號是「batteries included」，標準函式庫本身就很大。很多人一遇到需求就 pip install，其實先翻標準函式庫常常就夠了。

標準函式庫：一定要熟的那幾個

  • pathlib：物件導向的路徑操作，取代 os.path 那堆字串拼接。
  • collections：Counter（計數）、defaultdict（自帶預設值的 dict）、deque（兩端 O(1) 的佇列）、namedtuple。
  • itertools：chain、groupby、product、islice、batched（3.12+）等迭代積木。
  • functools：lru_cache / cache（記憶化）、partial、wraps、reduce、singledispatch。
  • dataclasses：自動產生 __init__、__repr__、__eq__ 的資料類別。
  • typing：型別提示用的各種工具。
  • json / csv / tomllib：常見資料格式讀寫，tomllib（3.11+）可以直接讀 pyproject.toml。
  • re：正規表示式。
  • datetime / zoneinfo：時間與時區，zoneinfo（3.9+）取代了第三方的 pytz。
  • logging：正式的日誌系統。
  • argparse：命令列參數解析。
  • subprocess：呼叫外部程式。
  • concurrent.futures / threading / multiprocessing / asyncio：併發四件套。
  • sqlite3：內建的嵌入式資料庫，做小工具、快取、離線分析非常好用。
  • hashlib / hmac / secrets：雜湊、訊息驗證碼、密碼學安全的亂數。產生 token 請用 secrets，不要用 random。
  • struct：把 bytes 依照 C 結構打包、解包，解析二進位檔案格式必備。
  • unittest / doctest：內建測試框架（實務上多半改用 pytest）。
from collections import Counter
from pathlib import Path

words = Path("article.txt").read_text(encoding="utf-8").split()
print(Counter(words).most_common(5))

for py in Path("src").rglob("*.py"):
    print(py.relative_to("src"), py.stat().st_size)

資料處理與科學計算

  • NumPy：N 維陣列與向量化運算，幾乎所有科學計算套件的地基。
  • pandas：表格資料（DataFrame）處理的事實標準。
  • Polars：Rust 寫的 DataFrame 函式庫，多核心、lazy 查詢，大資料量時常比 pandas 快很多。
  • Matplotlib / Seaborn / Plotly：畫圖，靜態到互動式都有。
  • SciPy：數值方法、統計、訊號處理、最佳化。
  • scikit-learn：傳統機器學習（分類、迴歸、分群、前處理）。
  • PyTorch：深度學習的主流框架。
  • Jupyter：互動式筆記本，探索資料的標準工作環境。

這一整區有個共通點：真正在跑的不是 Python，是底下的 C、C++、Fortran 或 Rust。Python 負責描述「要做什麼」，重活交給編譯過的原生程式碼。這也是為什麼「Python 很慢」跟「Python 是 AI 的主流語言」可以同時成立。

Web 與網路

  • requests：最廣為人知的 HTTP client，API 簡潔。
  • httpx：介面類似 requests，但同時支援同步與 async，也支援 HTTP/2。
  • FastAPI：以型別提示驅動的 API 框架，自動產生 OpenAPI 文件。
  • Flask：輕量 Web 框架，彈性高。
  • Django：全端框架，ORM、Admin、驗證全包。
  • Pydantic：用型別提示做資料驗證與序列化，FastAPI 的核心。
  • SQLAlchemy：資料庫工具包與 ORM。
  • Beautiful Soup / lxml：解析 HTML / XML。
  • Playwright / Selenium：瀏覽器自動化。

開發工具鏈

  • uv：Astral 用 Rust 寫的套件與專案管理工具，速度很快，可以一手包辦 Python 版本、虛擬環境、依賴鎖定。
  • pip + venv：官方內建的基本組合，任何環境都有。
  • Ruff：同樣來自 Astral 的 linter + formatter，取代 flake8、isort、Black 的大部分工作。
  • mypy / Pyright：靜態型別檢查器。
  • pytest：測試框架的事實標準，fixture 與參數化測試很好用。
  • pre-commit：在 commit 前自動跑檢查。
  • rich / Typer / Click：漂亮的終端輸出與命令列介面。

資安常用

Python 在資安領域幾乎是預設語言，分析、自動化、寫 PoC 都靠它。以防禦與研究用途來說，常見的有：

  • cryptography：正規的密碼學函式庫，不要自己發明加密演算法。
  • Scapy：建構與解析網路封包，做流量分析、協定研究。
  • pefile / LIEF：解析 PE、ELF 等執行檔格式，惡意程式分析的基本工具。
  • yara-python：用 YARA 規則比對樣本特徵。
  • Capstone / Unicorn：反組譯引擎與 CPU 模擬器。
  • pwntools：CTF 與漏洞研究的瑞士刀。
  • Volatility 3：記憶體鑑識框架。

Part 3：實務常用方法

會語法跟能寫出好維護的專案，中間差的是一堆「沒人教但大家都在用」的習慣。

虛擬環境與 pyproject.toml

每個專案一個虛擬環境，這是第一條規則。全域安裝套件遲早會遇到版本互相打架。

# 官方內建的做法
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install requests

# 用 uv 的做法
uv init my-tool
uv add requests
uv run python main.py            # 自動建立並使用 .venv

專案設定集中在 pyproject.toml（PEP 518 / PEP 621），名稱、版本、依賴、工具設定都放在這裡，requirements.txt 多半只剩部署鎖版本的用途。

[project]
name = "my-tool"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["httpx>=0.27", "pydantic>=2"]

[tool.ruff]
line-length = 100

另外一個常被忽略的：if __name__ == "__main__":。模組被 import 時 __name__ 是模組名，直接執行時才是 "__main__"。把執行入口包在裡面，檔案才能同時被 import 又被直接執行。

型別提示 + 靜態檢查

型別提示（type hints）在執行時不會被檢查。這是很多人誤解的地方：寫了 x: int，傳 str 進去程式照樣跑。它的價值在於讓 mypy、Pyright、IDE 在你執行之前就抓到錯。

from collections.abc import Iterable

def top_n(scores: dict[str, int], n: int = 3) -> list[tuple[str, int]]:
    return sorted(scores.items(), key=lambda kv: kv[1], reverse=True)[:n]

def first[T](items: Iterable[T]) -> T | None:   # 3.12+ 的泛型語法（PEP 695）
    return next(iter(items), None)

type UserId = int                              # 3.12+ 的型別別名

3.14 起，annotation 預設改成延遲求值（PEP 649 / 749），前向參照（還沒定義的類別名稱）不用再加引號。實務建議是：公開的函式介面一定寫型別，內部的小變數讓工具推斷就好。

dataclass 與資料建模

用 dict 傳資料很方便，直到某天打錯一個 key。結構固定的資料，請給它一個型別：

from dataclasses import dataclass, field

@dataclass(frozen=True, slots=True)    # frozen：不可變；slots：省記憶體、屬性存取更快
class Alert:
    host: str
    severity: int
    tags: list[str] = field(default_factory=list)   # 可變預設值要用 default_factory

a = Alert("web-01", 3)
print(a)   # Alert(host='web-01', severity=3, tags=[])

選擇的大原則：

  • dataclass：程式內部的資料結構，信任來源。
  • Pydantic model：外部輸入（API request、設定檔、使用者資料），需要驗證與轉型。
  • NamedTuple：小而不可變、需要像 tuple 一樣解包的紀錄。
  • TypedDict：資料本質上就是 JSON dict，只是想讓型別檢查器看懂它。

檔案、路徑與編碼

from pathlib import Path

base = Path(__file__).resolve().parent          # 以腳本所在位置為基準，不要依賴當前工作目錄
out = base / "output" / "report.json"           # 用 / 組路徑，跨平台
out.parent.mkdir(parents=True, exist_ok=True)
out.write_text(json.dumps(data, ensure_ascii=False, indent=2), encoding="utf-8")

永遠明確寫 encoding="utf-8"。在 Windows 上，沒寫的話預設編碼可能是 cp950 之類的系統編碼，同一支程式換台電腦就讀出亂碼。這個預設值正在改變中（PEP 686 計畫讓 UTF-8 mode 成為預設），但明確寫出來永遠不會錯。

logging 取代 print

print 適合除錯十分鐘，不適合跑在伺服器上三個月。logging 給你等級、時間戳、來源模組，以及「不改程式就能調整輸出」的能力。

import logging

logger = logging.getLogger(__name__)    # 每個模組一個 logger

def main():
    logging.basicConfig(
        level=logging.INFO,
        format="%(asctime)s %(levelname)s %(name)s: %(message)s",
    )
    logger.info("start scanning %s", target)    # 用 %s 參數，不要先 f-string 組好
    try:
        run()
    except Exception:
        logger.exception("scan failed")         # 自動附上 traceback

函式庫只負責 getLogger(__name__) 然後寫 log，設定 handler 是應用程式入口的事。函式庫自己呼叫 basicConfig 會搶走使用者的設定權。

併發：thread、process 還是 asyncio

選錯工具是 Python 效能問題最常見的來源。判斷只看一件事：你的程式在等什麼？

  • 等 I/O（網路、磁碟、資料庫），數量不多：ThreadPoolExecutor。等待 I/O 時會釋放 GIL，多執行緒一樣有效。
  • 等 I/O，數量上千、上萬：asyncio。單執行緒、事件迴圈切換，幾千個連線的成本遠低於幾千條 thread。
  • 在算東西（CPU 密集）：ProcessPoolExecutor，每個 process 有自己的直譯器和 GIL；或者把熱點交給 NumPy 這類會釋放 GIL 的原生函式庫。
from concurrent.futures import ThreadPoolExecutor
import httpx

def fetch(url: str) -> int:
    return httpx.get(url, timeout=10).status_code

with ThreadPoolExecutor(max_workers=16) as pool:
    for url, code in zip(urls, pool.map(fetch, urls)):
        print(url, code)
import asyncio
import httpx

async def main(urls):
    async with httpx.AsyncClient(timeout=10) as client:
        async with asyncio.TaskGroup() as tg:          # 3.11+：任一失敗會取消其他 task
            tasks = [tg.create_task(client.get(u)) for u in urls]
    return [t.result().status_code for t in tasks]

asyncio.run(main(urls))

asyncio 有一條鐵律：async 函式裡不能呼叫會阻塞的同步函式（例如 time.sleep、requests.get），否則整個事件迴圈都會卡住。真的要呼叫，用 asyncio.to_thread() 丟到執行緒去跑。

先量再優化

直覺猜的效能瓶頸，十次有八次是錯的。先量：

  • timeit：比較兩種寫法的小片段。
  • cProfile + snakeviz：看整支程式時間花在哪個函式。python -m cProfile -s cumtime app.py。
  • py-spy：取樣式 profiler，可以直接掛到正在跑的 process 上，不用改程式。
  • tracemalloc：追記憶體從哪裡配置出來。

量到瓶頸之後，有效的優化通常是這個順序：換演算法與資料結構（list 查找改 set）→ 減少重複計算（functools.cache）→ 向量化（交給 NumPy / Polars）→ 平行化 → 最後才是 Cython、Rust（PyO3）重寫熱點。

反過來說，在沒量過的程式上做微優化，就是過早的優化（premature optimization）。

Part 4：底層技術

從這裡開始換個視角：我們不再問「怎麼寫」，而是問「CPython 拿到這段程式碼之後做了什麼」。CPython 是 Python 的官方實作，用 C 寫成；PyPy、GraalPy 是其他實作，這裡講的細節都以 CPython 為準。

從原始碼到 bytecode

回到開頭那張圖，一個 .py 檔被執行前要經過四步：

  • Tokenizer：把文字切成 token（名稱、數字、運算子、縮排）。Python 的縮排在這一步被轉成 INDENT / DEDENT token，所以縮排是真正的語法。
  • Parser：把 token 組成抽象語法樹（AST）。3.9 起改用 PEG parser（PEP 617），取代了舊的 LL(1) parser，這也是後來 match 這類語法能加進來的原因。
  • Compiler：建立符號表（決定每個名稱是 local、global 還是 closure 變數）、做常數折疊等優化，再產生 bytecode，包進一個 code object。
  • Interpreter：執行 code object 裡的 bytecode。

每一步都可以從 Python 裡直接觀察：

import ast, dis

print(ast.dump(ast.parse("c = a + b"), indent=2))   # 看 AST

def add(a, b):
    c = a + b
    return c

dis.dis(add)                    # 看 bytecode
print(add.__code__.co_varnames) # ('a', 'b', 'c')
print(add.__code__.co_consts)

dis.dis(add) 在 3.12 會印出類似這樣的結果（省略 offset，不同版本的指令名稱會有差異）：

RESUME          0
LOAD_FAST       0 (a)
LOAD_FAST       1 (b)
BINARY_OP       0 (+)
STORE_FAST      2 (c)
LOAD_FAST       2 (c)
RETURN_VALUE

注意 LOAD_FAST：local 變數在編譯期就被分配好陣列索引，執行時直接用索引拿。global 變數則是 LOAD_GLOBAL，要查 dict。這就是「local 比 global 快」的真正原因，不是玄學，是指令不一樣。

另一個例子：3.12 之後 list / dict / set comprehension 被直接內聯（inline）到所在的函式裡（PEP 709），不再偷偷建立一個隱藏的函式物件，所以推導式比以前更快。

.pyc 快取

被 import 的模組，編譯結果會存在 __pycache__/模組名.cpython-312.pyc。檔頭是 16 bytes：一個 magic number（代表 bytecode 版本，不同 Python 版本不相容）、一組 flags，再來是原始檔的修改時間與大小（或是 PEP 552 的原始碼雜湊）。下次 import 時如果原始檔沒變，就直接載入 bytecode，跳過前三步。直接執行的主程式不會被寫成 .pyc。

直譯器迴圈與 Specializing Adaptive Interpreter

bytecode 最後交給 Python/ceval.c 裡的求值迴圈執行。概念上它就是一個巨大的 switch：

# 虛擬碼：CPython 的 eval loop 概念上長這樣（實際是 C）
while True:
    opcode, arg = next_instruction()
    match opcode:
        case LOAD_FAST:  stack.push(frame.locals[arg])
        case BINARY_OP:  right, left = stack.pop(), stack.pop(); stack.push(left + right)
        case RETURN_VALUE: return stack.pop()
        ...

CPython 是堆疊式虛擬機（stack-based VM）：指令從值堆疊（value stack）拿運算元，把結果推回去。每一次函式呼叫對應一個 frame，裡面放著這次呼叫的 local 變數、值堆疊、目前執行到哪一條指令。

3.11 是一個轉捩點，官方宣稱平均比 3.10 快約 25%。主要來自 Faster CPython 計畫的幾項改動：

  • Specializing Adaptive Interpreter（PEP 659）：一條指令被執行幾次之後，直譯器會依照實際看到的型別把它「特化」。例如 BINARY_OP 如果每次都是兩個 int 相加，就換成 BINARY_OP_ADD_INT，跳過一般化的型別分派；LOAD_ATTR 遇到固定形狀的實例，就換成直接從固定偏移量讀取的版本。猜錯了會退回一般版本。
  • 更輕的 frame：frame 改成在每個執行緒專屬的連續記憶體上配置，真正的 frame 物件只在有人需要（例如 traceback、sys._getframe()）時才建立。
  • Python 呼叫 Python 不再遞迴 C 堆疊：函式呼叫在同一個 eval loop 裡完成，呼叫成本大幅下降。
  • 零成本例外（zero-cost exceptions）：try 區塊在沒出錯時不再執行任何額外指令，改用例外表（exception table）在出錯時查詢。

你可以用 dis.dis(func, adaptive=True) 看特化後的指令。這也解釋了一個現象：型別穩定的程式碼跑得比較快。同一個變數一下 int 一下 str，特化就一直失敗。

PyObject：一切皆物件的真正意思

「Python 裡一切都是物件」這句話在 C 層面是字面意義：每個 Python 值都是一塊 heap 上的記憶體，開頭固定是一個 PyObject 標頭。

typedef struct _object {
    Py_ssize_t ob_refcnt;        // 參照計數
    PyTypeObject *ob_type;       // 指向它的型別
} PyObject;                      // 一般（有 GIL）建置下的簡化版本

ob_type 指向的型別物件（PyTypeObject）裡有一整排函式指標：怎麼相加（nb_add）、怎麼取屬性（tp_getattro）、怎麼雜湊（tp_hash）、怎麼釋放（tp_dealloc）。直譯器執行 a + b 時，做的事情就是「看 a 的型別，呼叫它的加法函式指標」。你在類別裡寫 __add__，CPython 就把對應的 slot 接到你的 Python 方法上。

list 存的是指向物件的指標，不是值本身。每一層物件開頭都是 ob_refcnt 與 ob_type。

從這張圖可以直接推出幾個 Python 的「怪現象」：

  • 為什麼 [[]] * 3 改一個三個都變：複製的是三個指向同一個 list 的指標。
  • 為什麼 Python 的 int 比 C 肥：一個小整數在 64 位元系統上要 28 bytes（sys.getsizeof(1)），因為它是一個完整物件，有標頭、有大小欄位、有數字陣列。
  • 為什麼 NumPy 快：NumPy 陣列存的是連續的原始數值，沒有每個元素一個物件的成本，CPU 快取也友善得多。

描述器與屬性查找

obj.attr 也不是單純查 dict。CPython 的查找順序是：

  • 1. 型別 MRO 上的資料描述器（data descriptor）：同時定義了 __get__ 和 __set__ 的東西，例如 property。
  • 2. 實例自己的 __dict__。
  • 3. 型別上的非資料描述器或一般屬性：函式就是非資料描述器，obj.method 會透過 __get__ 產生綁好 self 的 bound method。
  • 4. 都找不到才呼叫 __getattr__。

「MRO」是方法解析順序（Method Resolution Order），用 C3 線性化演算法算出來，可以用 Cls.__mro__ 看。super() 走的就是這條鏈上的下一個，所以在多重繼承裡 super() 不一定會呼叫到你以為的父類別。

list、dict、str 的實作

list：會多留空位的動態陣列

list 是一個 PyObject* 陣列，ob_size 是目前元素數，allocated 是實際配置的格數。append 塞滿時，CPython 不是只多要一格，而是大約多配置 1/8 再加上一點常數（Objects/listobject.c 的 list_resize）。因為成長是按比例的，攤銷（amortized）後 append 是 O(1)。上面那張圖的 list 只有兩個元素卻配置了 4 格，就是這個原因。

dict：緊湊雜湊表

3.6 之後的 dict 拆成兩個陣列：一個小的索引陣列（存放 entry 的位置），一個依插入順序排列的 entry 陣列（hash、key、value）。好處有兩個：記憶體更省（索引陣列可以用 1 byte 的整數），而且遍歷時天然就是插入順序，這就是「dict 有序」的由來。碰撞用開放定址（open addressing）加擾動探測解決，負載超過約 2/3 就擴容。

同一個類別的多個實例，屬性名稱通常一樣，所以 CPython 讓它們共用 key（PEP 412 的 key-sharing dict），3.11 之後更進一步，實例屬性在多數情況下直接存在物件內部，不需要真的建一個 __dict__。

str 的雜湊值預設帶隨機種子（hash randomization，用 SipHash），每次啟動不一樣。這是為了防止攻擊者刻意構造大量碰撞的 key 讓 dict 退化成 O(n) 的 hash flooding 攻擊。可以用環境變數 PYTHONHASHSEED 固定。

str：彈性表示法

3.3 起（PEP 393），字串會依照內容裡「最大的那個字元」決定每個字元用 1、2 還是 4 bytes 存。純 ASCII 一個字元 1 byte；出現中文就變 2 bytes；出現 emoji 這類超出 BMP 的字元就變 4 bytes。所以同樣長度的字串，sys.getsizeof 可能差好幾倍。字串不可變，所以可以安全地共用與快取，識別字這類短字串會被 intern。

int：任意精度

int 內部是一個「數字陣列」，在多數平台上每個 digit 存 30 bits，數字越大陣列越長，所以永遠不會溢位，代價是大數運算比 C 慢。另外，3.11 起（也回補到較舊的安全更新版本）int 與十進位字串互轉預設限制 4300 位數，因為那個轉換是二次方複雜度，超大數字可以被拿來做阻斷服務攻擊，可以用 sys.set_int_max_str_digits() 調整。

記憶體配置：pymalloc

Python 程式會建立、丟棄海量的小物件，每次都向作業系統的 malloc 要記憶體太慢。CPython 為此有自己的小物件配置器 pymalloc：

  • 小於等於 512 bytes 的請求才走 pymalloc，更大的直接交給系統 malloc。
  • 三層結構：向系統一次要一大塊 arena，切成 pool，每個 pool 只服務一種大小的 block。同大小的物件住在一起，配置與釋放都是從 free list 拿或放回去。
  • free list：float、tuple 等常用型別還有自己的回收清單，物件死掉後先留著，下次同型別要用直接重用。

這帶來一個常見的觀察：Python 程式釋放了大量物件，但作業系統看到的記憶體用量沒有下降。因為 arena 只有在裡面完全沒有活著的 block 時才會還給系統，零星幾個活物件就能把一整塊 arena 留住。

free-threaded 建置（下面會講）則改用 mimalloc 作為配置器，因為它天生就是為多執行緒設計的。

參照計數與垃圾回收

CPython 的記憶體回收有兩層。

第一層：參照計數（reference counting）

每次有新的參照指向物件（綁到名稱、放進 list、當參數傳），ob_refcnt 加一；參照消失就減一。歸零的那一刻，物件立刻被釋放。這帶來 CPython 很重要的一個特性：釋放時機是可預測的，檔案物件離開作用域就會被關掉（雖然你還是應該用 with）。

import sys
x = []
print(sys.getrefcount(x))   # 2：x 本身一個，傳進 getrefcount 當參數又一個

3.12 引入了永生物件（immortal objects，PEP 683）：None、True、小整數（-5 到 256）等物件的參照計數被設成一個特殊值，不再增減。這看起來是小事，實際上避免了大量對共享記憶體的寫入，對多核心與 fork 之後的 copy-on-write 都有幫助。

第二層：循環垃圾回收器（cycle GC）

參照計數有一個死穴：循環參照。A 指向 B、B 指向 A，兩個都沒人用了，但計數永遠不會歸零。

class Node:
    def __init__(self):
        self.other = None

a, b = Node(), Node()
a.other, b.other = b, a
del a, b      # refcount 都還是 1，只能靠 cycle GC 回收

gc 模組負責這件事。它只追蹤「能裝其他物件的容器」（list、dict、自訂類別實例等），定期找出「只被彼此參照、外界摸不到」的一群物件，整批回收。傳統上它是三代的分代式（generational）設計，基於「大部分物件都很短命」的觀察，新物件被檢查得最頻繁。3.14 把它改成增量式（incremental）回收，只分新、舊兩代，每次只處理一部分舊世代，目的是降低大型程式偶發的長暫停。

實務上要記得：能用參照計數處理掉的就不要留給 GC。需要「指著但不擁有」的關係（快取、觀察者、父節點反向指標），用 weakref 斷開循環。

GIL 與 free-threading

GIL（Global Interpreter Lock）是一把全域鎖：同一時間只有一條執行緒能執行 Python bytecode。

它存在的理由不是設計者偷懶，而是參照計數本身：每個物件的 ob_refcnt 隨時在被加減，如果多條執行緒同時改又沒有保護，計數就會錯，錯的結果是物件被提早釋放（崩潰）或永遠不釋放（洩漏）。一把大鎖是保護所有物件最簡單、單執行緒效能也最好的方案。

幾個常被講錯的地方：

  • GIL 不會讓多執行緒完全沒用。執行緒在做阻塞 I/O 時會釋放 GIL，NumPy、hashlib 這類 C 擴充在做大量計算時也會主動釋放。I/O 密集的程式用 thread 照樣有效。
  • GIL 不保證你的程式執行緒安全。直譯器預設每 5 毫秒（sys.getswitchinterval()）就可能要求切換，counter += 1 這種跨好幾條 bytecode 的操作照樣會出現競爭條件，該加鎖還是要加。
  • GIL 是 CPython 的實作細節，不是 Python 語言規格。Jython、IronPython 就沒有 GIL。

拿掉 GIL：free-threaded Python

PEP 703 提出可選的無 GIL 建置。3.13 以實驗性質推出（執行檔名稱通常是 python3.13t），3.14 依 PEP 779 轉為官方支援（但仍不是預設建置）。為了在沒有大鎖的情況下維持正確，它換了一整套機制：

  • Biased reference counting：建立物件的那條執行緒用不需要原子操作的快速路徑改計數，其他執行緒才用原子操作。
  • 延遲參照計數與更多 immortal 物件：減少熱門共享物件上的計數競爭。
  • 細粒度鎖：list、dict 等容器有自己的鎖，保證單一操作的一致性。
  • mimalloc：執行緒友善的記憶體配置器。

代價是單執行緒效能會下降一些，而且 C 擴充套件要宣告自己支援 free-threading，否則載入時會重新啟用 GIL。可以用 sys._is_gil_enabled() 檢查目前是否有 GIL。

另一條路線是子直譯器（subinterpreters）：3.12 讓每個子直譯器可以有自己的 GIL（PEP 684），3.14 在標準函式庫加入 concurrent.interpreters（PEP 734），定位介於 thread 和 process 之間：同一個 process 裡平行執行，但彼此的物件互相隔離。

JIT 與未來

3.13 起 CPython 加入了實驗性的 JIT 編譯器（PEP 744），用的是 copy-and-patch 技術：事先由 LLVM 把每種微指令（micro-op）編好成機器碼模板，執行時把模板複製出來、填上實際的參數。熱門的程式路徑會先被轉成一串微指令（tier 2），再交給 JIT 產生機器碼。

老實說，目前它的加速幅度還不大，預設也沒有開啟（3.14 的官方 Windows、macOS 安裝檔附有這個實驗性 JIT，可以用環境變數 PYTHON_JIT=1 啟用）。它的意義不在今天快多少，而在於基礎建設：特化直譯器負責收集型別資訊，JIT 負責把這些資訊變成機器碼，兩者疊起來，才是 Faster CPython 長期的方向。

從 3.11 的特化直譯器、3.12 的 immortal objects 與 per-interpreter GIL、3.13 的 free-threading 與 JIT、到 3.14 的增量 GC：這幾年 CPython 的改變，比過去十年加起來還多。

結語

學 Python 最常見的路徑是：先會語法，然後裝一堆套件，然後在某個效能問題或詭異的 bug 面前卡住。

卡住的原因通常不是語法不熟，是不知道語法背後的規則從哪裡來。可變預設值、is 和 ==、local 比 global 快、thread 跑 CPU 工作沒變快、釋放了物件記憶體卻沒降，這些看起來互不相干的「怪現象」，追到底都是同一套機制：名稱綁定、物件標頭、bytecode、參照計數、GIL。

懂了底層，不是為了每天去讀 ceval.c，而是讓你遇到問題時知道該往哪裡查。

語法讓你寫得出來，底層讓你知道為什麼會這樣。
